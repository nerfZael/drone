# Chat-load diagnostics

After rebuilding and restarting Hub and reloading the desktop UI, reproduce a
slow chat selection and find its `chat load timing` record in the active profile's
`drone/hub.log`. Each response's `requests[].requestId` matches a `hub HTTP request
timing` record. The ID is generated by Hub and returned as `x-drone-request-id`.

Compare these intervals (all in milliseconds):

- Browser Resource Timing: request start to response start measures waiting for
  response headers, including transport and delays before JavaScript runs.
- `hub_entry_to_route`: first Hub HTTP callback to chat route dispatch.
- Existing `Server-Timing` phases: the chat handler's work.
- `hub_entry_to_headers`: first HTTP callback to writing response headers.
- Server log `headersToFinishMs`: headers to Node's response `finish` event. This
  means handed off to the operating system, not delivered to the browser.

The new header timings also appear in the existing browser `serverTiming` object.
Do not add nested timings together: entry-to-route is part of entry-to-headers.
Chat reads are logged even when fast, because a slow browser request may reach
the handler late. Other API requests are logged at 250 ms; SSE stream lifetimes
are excluded. Query strings, credentials, and request bodies are not logged by
these diagnostics.

For waiting outside the handler, find overlapping `hub event loop stall` windows.
A 250 ms timer reports when it is at least another 250 ms late. Records include
process CPU usage, event-loop utilization, observed GC overlap, and memory usage.
High CPU suggests CPU work; substantial GC overlap suggests garbage collection.
Low CPU during a long stall can indicate blocking native work, process scheduling,
or host suspension. These are clues, not proof of a particular blocking function.
CPU covers the process (including worker threads), GC observations are best effort
and bounded to 128 recent entries, and memory is sampled after the stall.

No JavaScript timer measures time before the first HTTP callback executes. Use
browser timing and stall windows together for that gap; do not interpret a fast
entry-to-headers value as proof that Hub was responsive. Client/server wall clocks
may differ. Exact blocking-function attribution still requires a CPU profile;
these diagnostics do not automatically collect profiles or heap snapshots.

## Android/mobile loads

The mobile app records chat selections from tap through cached/fresh content
application, React layout-effect commit, and a double animation-frame callback.
`freshFrame` is a display proxy, not native frame presentation. The navigation
finishes as completed, error, timeout (45 seconds), superseded, or backgrounded.
Phone-local drone reads are measured too. A process killed before a navigation
finishes may leave no record of that unfinished load.

The latest 100 finished records live in the phone's AsyncStorage under
`droneHub.mobileChatLoads.v1`, including uploaded records. Pending records are
uploaded in batches of at most 10 per destination on reconnect/foreground and
every 15 seconds while active. Failed or unacknowledged uploads stay pending;
the oldest records are evicted when the buffer reaches 100. Remote-load records
go to their target Hub; phone-local loads go to the first connected Hub.

Uploads use the signed `device-core` operation `diagnostics.chat-load.upload`.
The receiving Hub takes the source phone ID from the authenticated request, never
from the submitted record. It stores validated fields in the `mobile_chat_loads`
table in the active profile's `drone/hub.sqlite`. Duplicate navigation IDs from
the same phone are ignored. On ingestion, retention removes records received
more than 30 days ago and caps history at 2,000 per phone / 10,000 overall.

Use the existing authenticated Hub API to investigate:

```text
GET /api/telemetry/mobile-chat-loads?deviceId=PHONE_ID&limit=1
GET /api/telemetry/mobile-chat-loads?droneId=DRONE_ID&chatName=default&since=2026-09-05T00:00:00Z
GET /api/telemetry/mobile-chat-loads?requestId=MESH_OR_HTTP_REQUEST_ID
```

Responses contain `records`, newest client `startedAt` first, with authenticated
`sourceDeviceId` and server `receivedAt`. `limit` defaults to 20 and is capped at
200. Querying before the first upload returns an empty history. Existing mobile
loads cannot be reconstructed retroactively.

Interpret a record using these measurements:

- `readRequested` to `coordinatorStarted`: app request coordination wait.
- `signedMs` and `sentMs`: offsets from the mesh request observation's start.
- `fetchMs` / `bodyMs`: HTTP headers wait and response-body read time.
- `serverPreInvokeMs`, `serverInvokeMs`, `serverPostInvokeMs`: target Hub request
  validation/admission, capability execution, and post-execution audit/encoding.
  The invocation includes any internal Hub API requests; these are not individual
  database-query timings.
- `server.hub_entry_to_headers`: outer Hub HTTP callback to headers. The
  `serverRequestId` matches `hub HTTP request timing` in `hub.log`; mesh chat reads
  retain these logs even when their HTTP handler is fast.
- `parseMs` / `decodeMs`: response JSON parsing and device-read delta/cache decoding.
- `freshResponse` to `freshApplied`: app comparison, cache, and state-update work;
  then `freshCommitted` and `freshFrame` cover the UI handoff.
- `maxJsTimerDelayMs`: worst observed delay of a 250 ms JS timer while loading.
  This is not an Android UI-thread profiler.

Intervals overlap; do not sum offsets or nested server timings. Missing fields
mean unobserved (for example an older Hub or a failed HTTP request), not zero.
Network time and pre-callback server stalls remain combined in headers wait;
compare with Hub stall windows and account for client/server clock differences.
Records include no prompts, message contents, URLs, tokens, or raw error text.

Activation requires rebuilt Hub/device-protocol code and updated mobile JS (or
an updated Android build), plus restarting Hub. No native Android module is added.
