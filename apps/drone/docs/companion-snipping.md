# Companion screenshots

In the desktop Hub, open Settings → Shortcuts and assign keys to **Snip image for Companion** and **Capture screen for Companion**. Enable **Global** on each binding to capture while another application is focused. They start unbound to avoid taking existing OS shortcuts.

Both actions are also in the Companion options menu, as **Snip part of the screen** and **Capture this screen**, which show the bound shortcut if there is one. Both actions target the monitor under the cursor. Snip freezes that screen and shows a selection rectangle with a control panel at the bottom, modelled on the GNOME screenshot tool. The rectangle starts where the previous snip left it (`snipping-selection.json` in the user data directory); drag inside it to move it, drag a corner or edge to resize it, or drag anywhere else to draw a new one. The panel switches between **Selection** (S) and **Screen** (C); the round button, Enter, Space, or Ctrl+C captures, and Escape or the close button discards the capture. The direct screen action skips the overlay.

On X11 the overlay covers every monitor, so the rectangle can be dragged onto, or across, any of them: a selection that crosses monitors is stitched into one image, with any gap between monitors left transparent, and **Screen** captures whichever monitor you click. The remembered rectangle is stored in screen coordinates; when the next snip starts on a different monitor, it appears at the same offset on that monitor. The display under the cursor is frozen before the overlay appears and the others a moment later; until then their live desktop shows through unchanged. Differently sized monitors are captured by separate, parallel requests so that no frame is rescaled. On other platforms the overlay covers only the monitor under the cursor.

The overlay window is created once, kept hidden, and reused. It is transparent and reveals the frozen frame only after that frame is decoded and the window covers the display, so it replaces identical pixels instead of flashing. On X11 it is a dock-type window: the window manager neither repositions it nor plays an open or close animation, which is also what lets one window span the whole desktop. Other Linux sessions anchor a small window on the target display and make it fullscreen before showing it.

Files can also be dragged onto Companion, or pasted after copying them in a file manager. The dropzone is decided by where the pointer is: the card together with its attachment row in the main window, and the whole window when Companion floats (its bar stops being a window drag region while files are dragged over it). A soft veil with “Drop to attach” covers the card while a drop would land. Any file is accepted, up to 100 MB: it is saved in `uploads/` and named to the model by path. Images and anything readable as text (`.txt`, `.md`, `.json`, source files and the like, kept under their own names) are also shown to the model directly when they are 6 MB or less. Other files appear in the tray as a chip with their extension, which opens them in Companion home; Companion can copy them with `transfer_files` or pass them to a drone with `attachmentPaths`. Only an empty item, such as a folder, is refused. There is no file picker. A copied image (for example from the system screenshot tool) pasted the same way becomes an image attachment named `pasted-image-*.png`; when the clipboard holds both an image and text, the image is used. Pressing Ctrl+V (Cmd+V) while Companion has focus — anywhere in its floating window, or inside its panel in the main window, outside an editable field — queues the clipboard text as a text attachment in the same way. Text attachments are stored beside captures in `uploads/` as `pasted-text-*.txt` and their content is inlined into the instruction (the first 200,000 characters), because Companion has no tool that reads Hub host files.

Attachments appear as a row of thumbnails just outside the Companion card, flush with its left edge: above it while content flows upward, below it when the floating bar sits high on the screen and content flows downward. The card itself stays a single bar. The row scrolls sideways when there are many, and hovering a thumbnail shows its remove button. Clicking one opens it in a dialog: text in a read-only Monaco editor, images in a viewer where the wheel zooms around the pointer, dragging pans, and double-click or the percentage button returns to fit.

Images appear as removable previews in Companion and accompany the next text, transcribed voice, or live-voice backend instruction. They are not sent merely by taking the screenshot. A failed or cancelled instruction restores its pending images; resetting Companion clears pending captures. Pending previews are held in memory until submission.

Submitted attachments are stored in Companion home, under `companion/home/uploads/` in the Hub data directory; a name that is already taken gets a numeric suffix instead of overwriting the earlier file. Each image is delivered to the model with its absolute path and its path relative to the home workspace (`uploads/<name>`). Companion can read, edit, or copy them with `transfer_files` from the `companion-home` target to a selected workspace with Write access. A `send_message` proposal may use `attachmentPaths: ["<absolute path>"]` for any image or text file in Companion home; proposal review displays those paths, and execution attaches the original bytes through the regular chat attachment pipeline. Files remain available after a turn or conversation reset. Captures stored by earlier versions under `companion/attachments/` stay valid as proposal attachments.

The number of attachments is not limited. Each capture or pasted text is uploaded to `uploads/` the moment it is taken (`POST /api/companion/home/uploads`), and an instruction then carries only the files' paths, so neither their count nor their combined size can make it fail; removing a pending attachment deletes its upload. A single file may be up to 6 MB. The model receives the first eight images inline, up to 20 MB together, and the first 200,000 characters of pasted text; any further images are listed by path with a note that they are not shown inline. Unsupported capture or missing screen-recording permission produces an error. Platforms that do not expose a matching display ID cannot reliably implement cursor-monitor capture; the action reports this instead of silently capturing a different screen. Browser-only Hub windows cannot use native capture.
