# Open Questions

These are the decisions to settle before implementation. Resolved decisions are kept here too so the project direction is easy to scan.

## Product Shape

Resolved:

- Desktop starts as an Electron app.
- Electron starts with a normal app window only.
- Voice Stream Next includes a Vite web dashboard.
- Voice Stream Next includes a Fastify backend.
- Voice and assistant are one product and one backend service.
- The web dashboard covers login, assistant threads, settings, transcripts, logs, and profile/account UI.
- The initial web dashboard includes a lightweight connected-device monitor.
- The connected-device monitor is admin-only.
- Admin access is controlled by a per-user `admin` boolean.
- The web dashboard does not need browser microphone capture or browser voice recognition in v1.
- Voice Stream Next remains separate from Drone Hub during the first implementation.

Open:

1. How should the first admin user be bootstrapped locally: environment variable, CLI command, or direct database edit during development?

## Naming

Resolved:

- Internal monorepo name: `voice-stream-next`.
- User-facing product name: Voice Stream.
- Voice Stream remains self-contained in `apps/voice-stream-next`.

Deferred:

- The old app can be archived or deleted later. No decision is needed now.

## Voice Behavior

Resolved:

- Keep behavior consistent across current Voice Stream clients first.
- Keep the same wake/sleep/status/approval phrases initially.
- Approval codes remain numeric.
- Lock, unlock, and off codes are per-user settings from the start.
- Per-user lock/unlock/off codes are seeded with defaults in the database and editable from web settings.
- Do not introduce a new push-to-talk-first model in v1.

Open:

1. Should changing voice codes require re-entering the current code, or is normal logged-in web settings access enough?

## Hosting And Auth

Resolved:

- Implement Clerk auth locally first.
- Host on Railway after local auth and persistence are working.
- Pairing tokens are per device.
- Client logs upload by default.
- Android should use Clerk's native Android SDK if viable.

Recommendation:

- For Electron, prefer using the same Vite/Clerk login UI in the normal app window if it works cleanly.
- If Electron redirect handling becomes painful, fall back to system-browser auth with a local callback or deep link.
- Do not build a manual device-code fallback in v1 unless Electron login proves unreliable.

Open:

1. Which Electron auth flow works cleanly with Clerk after the first implementation spike?

## Persistence

Resolved:

- Use `VOICE_STREAM_NEXT_DATA_DIR`.
- Store transcript history because it is user-visible.
- Store client logs as database rows.
- No time-based retention by default.
- No deletion controls in v1.
- No export flow in v1.
- Logs should be viewable, and copying relevant text to clipboard is enough for v1.

Open:

1. Should log rows store a structured `details_json` column from day one, or start with plain text plus level/source fields?

## Assistant Integration

Resolved:

- Assistant is part of the same Voice Stream Next backend.
- Assistant uses the same Clerk auth, SQLite database, web dashboard, and profile model.
- There is no separate Assistant Service in v1.
- Voice devices reuse the user's latest voice thread in v1.
- Spoken assistant responses are generated by the assistant module when speech output is requested.
- Voice Stream Next should add rich assistant thread parity without adding Drone Hub, drone, Docker, repo, or container control.
- The assistant parity target includes generic tools, approvals, model controls, system prompts, artifacts, spoken replies, streaming events, run lifecycle, voice thread mode, and non-drone capability scope.

Open:

1. Should latest voice thread reuse also account for user-selected assistant profile/settings?
2. Which first non-drone tool calls should require system approval?
3. Should artifact writes require approval, or only path/size validation?
4. Should spoken replies require approval in normal threads, voice threads, or neither?

## Drone Hub Integration

Resolved:

- No Drone Hub integration in the first implementation.
- Keep the services and apps flexible enough to add it later.

Deferred:

- Inbound vs outbound Drone Hub integration can be decided later.
- The first Drone Hub adapter surface can be decided later.

## Code Reuse

Resolved:

- Protocol schemas can live in a TypeScript package first.
- Test fixtures means shared examples and expected outputs, not shared runtime code.
- TTS means text-to-speech. STT means speech-to-text.
- Kotlin protocol models should use whatever is easiest at implementation time. Start with manual mirrored models if generation adds friction.

Context:

- Voice Stream Next server modules own speech-to-text and text-to-speech provider logic.
- Extracting means moving reusable pieces from those files into a shared package.
- Starting fresh means implementing the new Fastify backend without depending on those files, while reusing the ideas and behavior.

Recommendation:

- Start fresh in the new service first.
- Extract later only if the same provider code is needed by both legacy and next.
