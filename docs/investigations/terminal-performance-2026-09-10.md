Terminal startup and interaction performance — 2026-09-10

The largest opportunities are removing repeated startup work and replacing per-input tmux processes and polled logs with a persistent terminal connection. Both host and container drones use the expensive daemon input path once their WebSocket is connected. Container startup and HTTP fallback add Docker work and contention with unrelated drone operations.

This is an investigation and implementation proposal, not a shipped optimization. Source inspected at `dc9b2ae768`; measurements used Node 20.19.2, tmux 3.4 and Docker Engine 29.3.0 on the development host. No browser click-to-prompt, key-to-paint, production percentile, or stopped-container startup measurements were collected. The probes below isolate individual costs; their medians must not be presented as end-to-end timings.

**Startup: unnecessary work before a useful terminal**

The in-app sequence is: load the terminal module → initialize tabs/xterm → POST open → GET initial output → establish WebSocket → another daemon output request → establish daemon SSE → poll the log. The browser accepts input after POST open resolves, but until the WebSocket is open it uses the slower HTTP input route. Before a target is set, keystrokes are discarded.

1. **The first tab reopens after its successful open.** `shouldOpenDefaultShellSession` depends on the absence of `activeSession.sessionName`; `onResolveSessionName` fills it in; the flag is an open-effect dependency. The next effect resets the screen, input buffer and connection and posts open again. Changing chat name or drone display name also reruns the shell-open effect despite a stable terminal identity. Fix the effect around drone ID, terminal tab identity and explicit restart generation; resolving metadata must not restart it. [DroneTerminalDock.tsx](../../apps/drone-hub/src/droneHub/terminal/DroneTerminalDock.tsx), lines 138–143, 363–495.

2. **Switching terminal tabs rebuilds the connection and screen.** There is one xterm instance per dock, and switching active session runs the same reset/open/bootstrap sequence. Leaving the terminal tool pane can dispose the component too. Keep a bounded cache of terminal instances and connections keyed by drone, pane and session, restore focus immediately, and evict idle entries deliberately. Preserve server sessions independently of browser cache lifetime. [DroneTerminalDock.tsx](../../apps/drone-hub/src/droneHub/terminal/DroneTerminalDock.tsx), lines 313–355, 400–495; [RightPanelTabContent.tsx](../../apps/drone-hub/src/droneHub/app/RightPanelTabContent.tsx), lines 489–511.

3. **Container prewarm only creates a shell.** It waits 150 ms, excludes host drones, and does not share the in-flight open promise with the actual terminal. Opening the pane still repeats validation and attachment work. Preload the terminal module and share a deduplicated ensure-session operation, including host drones when appropriate. Start with the selected drone or user intent; do not eagerly allocate terminals across the fleet. Invalidate by runtime generation and session closure. The existing built terminal JS asset was about 352 KB uncompressed; no transfer/decode timing was measured. [terminal-prewarm.ts](../../apps/drone-hub/src/droneHub/app/terminal-prewarm.ts); [use-drone-hub-app-model.tsx](../../apps/drone-hub/src/use-drone-hub-app-model.tsx), lines 2665–2720.

4. **Container open and initial replay wait for a broad drone lock.** `withLockedDroneContainer` uses the same operation lock as other drone mutations. Warm opens still run the dead-pane check, container readiness/restart-policy checks, tmux availability check and session-exists check. Each DVM session read also checks container/tmux readiness and performs separate size and text execs. Route terminal I/O through the already-running daemon and use a narrow session creation lock. Keep container lifecycle coordination for actual starts/restarts, with explicit generation invalidation. Use direct resolved-container exec for unavoidable setup. [terminal-route-service.ts](../../apps/drone/src/hub/terminal-route-service.ts), lines 220–275, 451–491, 577–583; [chat-session-runtime.ts](../../apps/drone/src/hub/chat-session-runtime.ts), lines 362–400; [api.ts](../../apps/dvm/src/api.ts), lines 446–510, 522–620; [server.ts](../../apps/drone/src/hub/server.ts), lines 1109–1132.

5. **Host replay reads the beginning of the log.** The Hub asks for `tail=40` but passes `since=0`; the daemon's log view ignores `tail` and reads forward from zero, up to 200 KB. A long-lived terminal initially shows stale history and then catches up through SSE. Implement a bounded recent snapshot with an exact continuation cursor. Raw tail fragments can begin inside terminal escape sequences, so a reconnect snapshot must account for terminal state, not just the last N newline-delimited records. Also, the host creates the shell before attaching `pipe-pane`, so a fast initial prompt can escape logging. [terminal-route-service.ts](../../apps/drone/src/hub/terminal-route-service.ts), lines 419–447; [daemon.ts](../../apps/drone/src/daemon.ts), lines 2242–2249, 2355–2400.

The existing in-app shell path already avoids skill/MCP synchronization. Keep that behavior. Repeated host readiness probes and nested login-shell wrappers are additional candidates to measure after eliminating duplicate opens; retain user shell configuration semantics.

**Typing and sustained output: structural costs**

Ordinary isolated keystrokes wait 22 ms in the frontend and another 24 ms in the Hub. The daemon then checks `has-session`, checks `pane_dead`, starts `load-buffer`, and starts `paste-buffer`. Four subprocesses are executed for every flushed batch, including batches containing only one character. The Hub serializes those HTTP calls. [DroneTerminalDock.tsx](../../apps/drone-hub/src/droneHub/terminal/DroneTerminalDock.tsx), lines 223–310; [terminal-websocket-server.ts](../../apps/drone/src/hub/terminal-websocket-server.ts), lines 6–10, 77–104, 298–309; [daemon.ts](../../apps/drone/src/daemon.ts), lines 1079–1114, 1370–1400, 2329–2351.

Output is `tmux pipe-pane → disk log → 25 ms daemon polling → SSE JSON → Hub parsing → WebSocket JSON → xterm`. An idle stream performs roughly 40 file-stat checks per second; active reads additionally open, allocate, read and close a file. Each subscriber owns a poll loop. Ten idle streams therefore imply roughly 400 stat checks per second, before filesystem latency. Output polling alone adds up to roughly 25 ms of scheduling delay under otherwise idle conditions; this is a code-derived interval, not measured key latency. [daemon.ts](../../apps/drone/src/daemon.ts), lines 1499–1531, 2420–2464.

First remove the stacked batching windows for ordinary input: send immediately when idle, coalesce only while a previous write is in flight, and preserve a single ordered input queue. HTTP fallback currently overlaps with WebSocket availability, so changing transports must not reorder command fragments. Simply deleting all batching while retaining four subprocesses per event could increase CPU cost.

For the larger improvement, use a persistent bidirectional connection from browser through Hub to the drone daemon. Prototype a daemon-owned tmux control-mode client to retain existing persistent sessions while eliminating per-keystroke process startup and log polling. Control mode accepts commands and emits pane output asynchronously. A PTY-backed tmux attachment is an alternative if full attachment semantics are required; compare resizing, terminal modes and reconnect behavior before selecting it. This recommendation follows the capabilities documented in the [tmux control-mode guide](https://github.com/tmux/tmux/wiki/Control-Mode), not a measured speedup of an implementation here.

Use one live reader per session with fan-out to subscribers, bounded replay and a clear session generation. Send terminal bytes without repeatedly decoding/re-encoding them. Keep logging outside the live delivery path. Both host and container implementations should expose the same daemon protocol; Docker should be needed for provisioning/recovery, not ordinary input or replay on a healthy daemon.

**Rendering and correctness that must accompany speed work**

- Make connection initialization non-consuming. The Hub's `max:1` output query and the daemon SSE initializer both discard their returned chunks. Preserve the requested offset, or transmit every consumed byte. Add tests for output arriving between snapshot and stream attachment, and for reconnects with backlog. [terminal-websocket-server.ts](../../apps/drone/src/hub/terminal-websocket-server.ts), lines 225–259; [daemon.ts](../../apps/drone/src/daemon.ts), lines 2426–2434.
- Preserve raw bytes and terminal control sequences. Decode incrementally or deliver binary data to xterm; stop sanitizing live chunks. Test Unicode and ANSI sequences split at every boundary. [daemon.ts](../../apps/drone/src/daemon.ts), lines 1522–1525; [DroneTerminalDock.tsx](../../apps/drone-hub/src/droneHub/terminal/DroneTerminalDock.tsx), lines 73–80, 198–207.
- Add bounded flow control through daemon, Hub, socket and renderer. Neither the SSE writer nor Hub sender checks backpressure, and xterm writes have no acknowledgement path. Both input queues silently retain only the last 128K string units on overflow, potentially changing pasted commands. Use explicit limits and ordered accepted-input semantics; never silently truncate commands or blindly retry input after uncertain delivery. The [xterm flow-control guide](https://xtermjs.org/docs/guides/flowcontrol/) describes write callbacks and upstream flow control. A write callback signals processing, not physical screen paint.
- Wire dimensions through to the backend. `ResizeObserver` calls only `fitAddon.fit()`; no terminal resize message/route is present in this path, and detached tmux creation receives no frontend rows/columns. Send initial dimensions with attach, then coalesce resize updates once per animation frame and send only changed sizes. Define which subscriber controls dimensions when several views share a session. [DroneTerminalDock.tsx](../../apps/drone-hub/src/droneHub/terminal/DroneTerminalDock.tsx), lines 317–343; [daemon.ts](../../apps/drone/src/daemon.ts), lines 1307–1324.
- Measure the renderer after transport fixes. The installed xterm defaults to DOM rendering; this app loads Fit and WebLinks, with 15,000 scrollback lines. Try the [official WebGL addon](https://github.com/xtermjs/xterm.js/blob/master/addons/addon-webgl/typings/addon-webgl.d.ts) for high-output workloads with context-loss fallback. Lazy-load it after initial usability so GPU initialization does not block opening. Do not add a second unconditional frame delay to every keystroke; xterm already schedules its write processing. Live output already writes directly through a ref, so there is no React transcript rebuild per chunk to eliminate.

**External terminal windows have a separate delay**

The `/open-terminal` route awaits skill, MCP and repository-instruction synchronization even in plain shell mode, for both runtimes. Move shell-independent agent preparation off that launch path. Container agent launch also performs five sequential tmux tuning execs that can be consolidated. [terminal-route-service.ts](../../apps/drone/src/hub/terminal-route-service.ts), lines 642–648, 721–746.

`spawnTerminalWithBash` imposes an 800 ms grace period before checking its launch marker. A window may already be open and typable during that wait, so this is a fixed API/UI completion delay, not proof of an 800 ms delay to actual window appearance. Observe marker arrival and child failure concurrently, return once startup is confirmed, and retain fallback behavior for launchers that silently fail. [server.ts](../../apps/drone/src/hub/server.ts), lines 3557–3619. The marker currently proves the wrapper started, not that the target shell is ready.

**Recommended implementation sequence and acceptance measurements**

1. Add terminal-specific timing milestones and regression coverage while fixing duplicate opens, consuming cursors, live sanitization, initial replay and dropped early input. Record click, module ready, open start/end, lock wait, session reuse/create, stream ready, first output processed and first echoed input. Keep contents and credentials out of timing records.
2. Introduce a fast ensure-and-attach operation with bounded snapshot/continuation, shared prewarm, stable tab identity and cached active/recent terminals. Remove Docker discovery and broad locks from healthy terminal reads/input. Adapt HTTP fallback to the same daemon semantics.
3. Introduce the persistent daemon transport with byte-preserving output, ordered input, resize, backpressure, exit notification and session-generation recovery. Remove stacked input timers and file polling from the live path. Retain safe reconnect and persistence behavior.
4. Compare DOM/WebGL, scrollback cost, hidden-tab resource use and paste/output stress. Choose based on traces rather than making renderer replacement a prerequisite for the earlier wins.

Suggested targets for an already-running local drone, to validate rather than promise: cached tab switch within one or two display frames; warm click-to-usable terminal below 100 ms p95; ordinary key-to-visible-echo below 30 ms p95. Measure stopped-container boot separately. Track p50/p95/p99 for both runtimes, with cold module load, new shell, reused shell, tab switch, reconnect, concurrent repository operations, idle fleet load and heavy output. Verify early typing, large paste, control keys, TUI redraw, Unicode, resize and reconnect preserve exact behavior. Record renderer processing and frame scheduling separately from actual paint where available.
